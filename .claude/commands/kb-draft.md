Создать черновик статьи во внутренней базе знаний поддержки из произвольного материала (ответ клиенту, переписка, заметка, инструкция).

Команда берёт сырой текст, превращает его в нормальную статью БЗ по структуре проекта и сохраняет **черновиком** (`status='draft'`) в таблицу `support_kb_articles` через n8n-вебхук. Черновик не виден клиентам — его потом дочитывают/проверяют и публикуют вручную в ERP (Поддержка → База знаний).

---

## 0. Что подаётся на вход

Аргумент команды (`$ARGUMENTS`) или последний обсуждавшийся материал — это **содержание** будущей статьи: ответ клиенту, кусок переписки, инструкция, разбор проблемы. Если входной материал пустой и в диалоге нет очевидного источника — спроси у пользователя, из чего делать статью, и не выдумывай факты.

Не добавляй ничего, чего нет в исходнике или в коде проекта. Если для структуры не хватает раздела (например, «Как проверить») — лучше опусти его, чем придумывай.

## 1. Достань конфиг вебхука

База знаний живёт в n8n LootArena, поэтому конфиг один и тот же из любого репозитория. Сначала попробуй взять его из `.env` текущего репо:

```bash
grep -hE '^VITE_API_BASE_URL=|^VITE_WEBHOOK_SECRET=' .env .env.local 2>/dev/null
```

- `VITE_API_BASE_URL` — база вебхуков, по умолчанию `https://n8n.lootarena.ru/webhook`.
- `VITE_WEBHOOK_SECRET` — секрет для заголовка `x-webhook-secret`.

Если в этом репозитории ключей нет (бэкенд-сервисы, лендинги и т.п.):
- базу бери по умолчанию — `https://n8n.lootarena.ru/webhook`;
- секрет `x-webhook-secret` возьми из `.env` репозитория `erp-lootarena` (`VITE_WEBHOOK_SECRET`) или из настроек n8n. **Не хардкодь секрет в файлы этого репозитория.**

Полный URL эндпоинта: `${VITE_API_BASE_URL}/erp/support/kb`. Это тот же воркфлоу, что использует ERP (`erp-lootarena/components/erp/support/KnowledgeBaseView.tsx`, функция `saveArticle`).

## 2. Сформируй поля статьи

Разбери исходный материал и заполни:

- **title** — короткий понятный заголовок по сути материала.
- **slug** — латиница, kebab-case, уникальный (напр. `tv-widget-fullscreen-kiosk`). Если такой slug может уже существовать — добавь различающий суффикс.
- **summary** — 1–2 предложения: о чём статья и кому полезна.
- **product_area** — строго одно из: `erp`, `guest_app`, `tv_widget`, `site`. Выбирай по теме материала.
- **product_platform** — только если `product_area = guest_app`: одно из `web`, `tg`, `max`, `ios`, `android`. Во всех остальных случаях — `null`.
- **audiences** — массив из `internal`, `owner`, `manager`, `employee`, `guest`. Для инструкций владельцам/управляющим клуба → `["internal","owner","manager","employee"]`. Внутренние ранбуки → `["internal"]`. Материалы для гостей → добавь `guest`.
- **tags** — 3–6 коротких тегов (рус/лат), по которым статью найдут поиском.
- **status** — всегда `draft`. (Команда создаёт именно черновик; публикует человек в ERP.)

## 3. Напиши body (markdown) по структуре БЗ

Рендерер статей кастомный (`MarkdownRenderer` в `KnowledgeBaseView.tsx`). Поддерживается: заголовки `#`–`####`, маркированные списки (`-`), нумерованные (`1.`), `**жирный**`, `` `inline-код` ``, горизонтальная линия `---`, медиа `![alt](https://…)`, автоссылки. **Таблицы и блоки ``` не поддерживаются** — не используй их. Команды/клавиши/пути оформляй inline-кодом в одинарных бэктиках. Между блоками оставляй пустую строку (иначе соседние строки склеятся в один абзац).

Базовый порядок разделов (бери только те, что реально нужны материалу):

```
# Заголовок статьи

## Коротко
1–3 предложения: суть и итог.

## Где находится
Где это в продукте/ERP/устройстве.

## Как настроить   (или ## Как использовать / ## Как сделать)
Пошаговые действия. Для разных платформ — подзаголовки ###.

## Как проверить
Как убедиться, что сработало.

## Частые ошибки
Типичные грабли и что с ними делать.

## Ограничения
Что не поддерживается / краевые случаи.

## Связанные статьи
Ссылки на смежные материалы (если есть).
```

## 4. Создай черновик через вебхук

Сначала покажи пользователю заголовок, slug, product_area, audiences и краткое содержание body. После подтверждения — отправь запрос. Подставь значения из .env и собранные поля:

```bash
curl -sS -X POST "${VITE_API_BASE_URL}/erp/support/kb" \
  -H "Content-Type: application/json" \
  -H "x-webhook-secret: ${VITE_WEBHOOK_SECRET}" \
  -d @- <<'JSON'
{
  "action": "create_article",
  "is_super_admin": true,
  "slug": "<slug>",
  "title": "<title>",
  "summary": "<summary>",
  "body": "<body markdown>",
  "product_area": "<erp|guest_app|tv_widget|site>",
  "product_platform": null,
  "audiences": ["internal","owner","manager","employee"],
  "tags": ["<tag1>","<tag2>"],
  "status": "draft",
  "created_by": "claude-code",
  "created_by_name": "Claude Code (kb-draft)",
  "updated_by": "claude-code"
}
JSON
```

> Тело JSON удобнее собрать в файл `/tmp/kb-draft.json` (правильное экранирование переводов строк в `body`) и отправить через `-d @/tmp/kb-draft.json`.

Ответ — массив с созданной статьёй; запомни её `id`.

## 5. (Опционально) Проиндексируй для AI-чата

Чтобы черновик попал в RAG-поиск по БЗ, можно дёрнуть индексацию (как делает UI после сохранения):

```bash
curl -sS -X POST "${VITE_API_BASE_URL}/erp/support/kb-ai" \
  -H "Content-Type: application/json" \
  -H "x-webhook-secret: ${VITE_WEBHOOK_SECRET}" \
  -d '{"action":"index_article","is_super_admin":true,"article_id":"<id>"}'
```

Для обычного черновика этот шаг можно пропустить — индекс всё равно обновится при сохранении/публикации из ERP.

## 6. Итог

Покажи пользователю:
- ✅ Заголовок и `slug` созданного черновика
- `id` статьи и её `product_area` / `audiences`
- Напоминание: проверить и опубликовать в ERP → **Поддержка → База знаний** (черновик клиентам не виден)
