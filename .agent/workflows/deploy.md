# Деплой

Dokploy настроен на автодеплой по тегу (Trigger Type: On Tag).
При пуше тега Dokploy автоматически подхватывает код из GitHub и деплоит.

> **Первый шаг**: прочитай `.agent/toolkit.json` → секцию `project` для получения имени проекта, n8n URL, webhook-пути, `dokploy_app_id` и исключений для .dockerignore.

> **⚠️ Если `dokploy_app_id` отсутствует** — ОСТАНОВИ деплой и попроси пользователя настроить:
>
> 1. Открыть Dokploy → найти приложение
> 2. Скопировать Application ID из URL или настроек
> 3. Добавить `"dokploy_app_id": "<ID>"` в `toolkit.json` → `project`
> Без этого уведомление в Telegram проверит статус не того приложения!

## Шаги

// turbo-all

### 0. Проверь .dockerignore (автоматически)

```bash
test -f .dockerignore && grep -qE "^\.git$" .dockerignore && grep -qE "^node_modules$" .dockerignore && echo "✅ .dockerignore OK" || echo "❌ .dockerignore требует внимания"
```

Если `.dockerignore` отсутствует или не содержит минимальных исключений (`.git`, `node_modules`):

- Создай файл автоматически на основе `.gitignore` + добавь: `.git`, `.agent`, `.claude`, `.agents`, `.gemini`, `specs`, `*.md`, `LICENSE`
- Добавь подпроекты из `toolkit.json` → `project.dockerignore_exclude`
- Закоммить `.dockerignore` перед деплоем

### 0.3. Typecheck и хуки — на ВСЁМ, что выпускаем

```bash
if grep -q '"check:hooks"' package.json 2>/dev/null; then
  NODE_OPTIONS=--max-old-space-size=8192 npx tsc --noEmit && npm run --silent check:hooks \
    || echo "❌ TYPECHECK/ХУКИ КРАСНЫЕ — НЕ ТЕГИРОВАТЬ"
fi
```

`vite build` типы не проверяет, а хук под ранним `return` роняет весь экран — ни сборка, ни `tsc` его не видят.
Обязателен после вливания чужих веток (облачных, коллеги): каждая проверялась ОДНА, вместе они могут не собраться.
`tsc` должен дойти до конца (код 0 и пустой вывод), а не упасть по памяти.

### 0.5. Проверь стартовый бандл (автоматически, если в проекте есть сторож)

```bash
if grep -q '"check:bundle"' package.json 2>/dev/null; then
  npm run build && npm run check:bundle || echo "❌ СТОРОЖ БАНДЛА КРАСНЫЙ — НЕ ТЕГИРОВАТЬ"
else
  echo "ℹ️  check:bundle в проекте нет — шаг пропущен (подключение: configs/react/SPA-HARDENING.md в agent-toolkit)"
fi
```

Ловит то, чего не видят ни `tsc`, ни `vite build`, ни телеметрия: **приложение, которое не
открывается вообще**. По собранному `dist` проверяет, что в стартовых чанках нет API новее
минимального поддерживаемого Safari, что синтаксис парсится под него и что стартовый бандл не
растолстел больше чем на 12% (рост почти всегда значит «пакет уехал в стартовый чанк и теперь
исполняется у всех»).

Красный — **не тегировать**. Лечение почти всегда одно: пакет, нужный в одном разделе, вынести из
стартового чанка (`manualChunks` → `undefined`, либо статический `import` → `await import()`).
Пакет действительно нужен на старте — обнови линию `npm run check:bundle -- --update-baseline` и
скажи об этом в changelog.

> Повод: 18–22.09.2026 в ERP LootArena `pdfjs-dist` четыре дня ехал в стартовом чанке и трогал
> `Iterator.prototype`, которого нет до Safari 18.2. На iOS 18.0/18.1 приложение не открывалось
> ВООБЩЕ (6 устройств из 6), а всё выглядело исправным: сборка зелёная, в логах сплошные 200,
> телеметрия пустая — она в том же бандле, который не исполнился.

### 0.6. Ревью по риску — страховка перед тегом (если в проекте есть `REVIEW.md`)

Коммиты с последнего тега, задевшие пути Высокого уровня, но без строки `Ревью:` в теле — они пришли мимо `/save`
(вливание облачной ветки, коммит коллеги, ручной коммит):

```bash
if [ -f REVIEW.md ]; then
  LAST=$(git describe --tags --abbrev=0)
  for h in $(git log --format=%h "$LAST..HEAD" -- $(awk '/^```text review-high-paths/{f=1;next} /^```/{f=0} f' REVIEW.md)); do
    git log -1 --format=%b "$h" | grep -q '^Ревью:' || git log -1 --format='без ревью: %h %an — %s' "$h"
  done
fi
```

Пусто — дальше. Есть строки — **ревью до тега**: субагент со свежим контекстом (или `/security-review`) по
`git diff $LAST..HEAD -- <файлы этих коммитов из списка Высокого уровня>`, правила — `REVIEW.md` + профильные
`specs/lessons/*`. Счёт находок и каждую «Важно» — в сводку перед тегом: исправить или закрыть с причиной. SQL из
миграций к этому моменту уже работает в проде: «Важно» там — живая дыра, чинить сразу, не дожидаясь тега.

### 1. Убедись что все изменения закоммичены

```bash
git pull --rebase origin main && git status
```

Если есть незакоммиченные изменения — сначала выполни `/save`.
Если pull подтянул чужой деплой (новый тег) — предупреди пользователя.

**Облачные сессии** (ERP LootArena): их работа приходит ветками `origin/claude/*` — облако не пушит в `main`, не
ставит тег, не применяет миграции и не удаляет ветки. Влить, применить «Требует применения: …» из коммитов ДО тега
и после релиза удалить влитые ветки на origin — по [`specs/devops/cloud-sessions.md`](../../specs/devops/cloud-sessions.md).

**И проверь, что в релиз не забыта работа из веток — сторожем, а не глазами:**

```bash
git fetch -q origin
if grep -q '"check:branches"' package.json 2>/dev/null; then
  npm run check:branches || echo "❌ В РЕЛИЗ НЕ ПОПАДЁТ ГОТОВАЯ РАБОТА — НЕ ТЕГИРОВАТЬ"
else
  # Сторожа в проекте нет — ручная страховка. Подключение: scripts/check-branches.mjs
  # (+ test-check-branches.mjs) из ERP LootArena и "preversion": "node scripts/check-branches.mjs".
  for b in $(git branch --format='%(refname:short)' | grep -v '^main$'); do
    n=$(git rev-list --count main..$b 2>/dev/null)
    [ "$n" != "0" ] && printf '⚠️  %-42s %s коммит(ов) НЕ в main\n' "$b" "$n"
  done
  git worktree list --porcelain | grep '^worktree ' | sed 's/^worktree //' | while read -r wt; do
    [ "$wt" = "$PWD" ] && continue
    n=$(git -C "$wt" status --short 2>/dev/null | wc -l | tr -d ' ')
    [ "$n" != "0" ] && printf '⚠️  %-42s %s незакоммиченных файл(ов)\n' "${wt##*/}" "$n"
  done
fi
```

Сторож (`scripts/check-branches.mjs`, стенд `node scripts/test-check-branches.mjs`; есть в
lootarena-app и ERP LootArena) проходит по ВСЕМ веткам — локальным и в origin — и по соседним worktree.
Блокирует: ветку, чьё содержимое НЕ в HEAD (решает `git merge-tree`, а не счёт коммитов —
squash-слитая ветка не мешает), конфликтующую ветку, `origin/main` впереди тебя («сначала git pull»)
и незакоммиченное в соседнем worktree. Он же стоит в `preversion`, поэтому `npm version` без него
версию не поднимет. Код 2 — проверка не отработала: это не зелёный. Ветку-копию после rebase
(её патчи уже лежат в HEAD другим SHA) он узнаёт через `git cherry` и не блокирует.

Что-то нашлось — **не тегируй молча**: либо влей в `main`, либо выпусти без этого ОСОЗНАННО —
`npm run check:branches -- --allow <ветка|каталог worktree>` (для `npm version` —
`CHECK_BRANCHES_ALLOW=<a>,<b>`) — и назови пользователю, что именно остаётся за бортом и почему.
«Ветка старая» — это вывод, который делают ПОСЛЕ сверки содержимого с `main`, а не по имени
или дате ветки.

**Архивы уборки (шаг 0.4 `save.md`) живут в реестре `scripts/check-branches.archive`.** Архивная
ветка на origin «впереди» HEAD навсегда (снимок worktree на старой базе, перенесённый патчем),
поэтому сторож знает её по SHA: `ported` — перенос сверен, молчит; `parked` — осознанно НЕ
перенесено, не блокирует, но печатается на каждом прогоне (назови такие пользователю); `dropped` —
устарело и переноситься не будет (решение принято), только считается в итоге. Новый коммит в
архив снова делает его красным. Запись — только после сверки содержимого и только с согласия
пользователя для `parked`/`dropped`:
`npm run check:branches -- --register origin/claude/x ported "что сверено"`.

> Повод: v1.62.0 и v1.63.0 приложения (23–25.09.2026) вышли мимо четырёх готовых веток — ручную
> проверку не прогнали. В ERP первый же прогон сторожа 25.09.2026 нашёл ~20 архивов уборки
> 14.09 с уроками и спеками, которых в `main` нет вовсе: уборка удалила их локально, не перенеся.

**А после успешного релиза — УБЕРИ то, что подтвердил** (`save.md`, шаг 0.4). Иначе этот же
список ты будешь разбирать на следующем теге, и на следующем: разбор растёт линейно с числом
накопленных веток (замер ERP 14.09.2026 — 34 ветки, 28 worktree, **8.7 ГБ**, ~15–20k токенов
за релиз; после уборки шаг 0 отдаёт одну строку за 0.03 с).

Порядок нерушим — **архив → сверка → удаление**:

```bash
# архив: незакоммиченное в worktree → коммит его ветки → push всех веток с работой
# сверка: git rev-parse <b> == git ls-remote --heads origin <b>   (иначе НЕ УДАЛЯТЬ)
# удаление: git worktree remove --force + git branch -D
```

Ветки, которой нет на `origin`, не существует нигде, кроме этого диска, а
`git worktree remove --force` уносит незакоммиченные файлы — ровно те, ради которых шаг 0
и появился. Не удаляй ветку, работу которой ещё не подтвердил маркером: гигиена идёт ПОСЛЕ
проверки, а не вместо неё.


### 2. Собери changelog (ПОДРОБНО!)

#### 2.1. Посмотри коммиты с последнего тега

```bash
git log $(git describe --tags --abbrev=0 2>/dev/null || echo "--all --reverse --format=%H | head -1" | xargs git log --oneline)..HEAD --oneline --no-decorate
```

#### 2.2. Посмотри ВСЕ изменённые файлы

```bash
git diff $(git describe --tags --abbrev=0 2>/dev/null)..HEAD --stat
```

#### 2.3. Просмотри DIFF ключевых файлов

**ОБЯЗАТЕЛЬНО** просмотри `git diff <last_tag>..HEAD -- <file>` для каждого значимого файла (экраны, компоненты, хуки, стили). НЕ полагайся только на заголовки коммитов — они часто неполные!

```bash
git diff $(git describe --tags --abbrev=0)..HEAD -- "*.tsx" "*.ts" "*.css"
```

#### 2.4. Сформируй **подробный технический changelog на русском**

**Правила changelog:**

- Группируй по категориям: 🆕 Новое / 🔧 Исправления / ⚙️ Инфраструктура
- Пиши **технически**: указывай затронутые компоненты, файлы, типы данных
- Для каждого пункта — **что изменилось**, **в каком компоненте**, **почему** (если не очевидно)
- Мелочи (переименования, импорты, форматирование) можно опускать
- Цель — по changelog можно понять контекст и при необходимости откатиться
- **Пункт Высокого уровня** (`REVIEW.md`: доступ, деньги, миграции, n8n, ПК-агент) — две строки под ним:
  `Риск:` что сломается и у кого, если пункт неверен; `Как откатить:` тег откатывает только фронт — для БД
  назови `specs/db/migrations/_rollback/…`, для n8n — `before.json` патча, или прямо «назад несовместимо».

**Плохой пример:**

```
• Гео-сортировка клубов
```

**Хороший пример:**

```
• **Гео-сортировка клубов** — `ClubList`: клубы сортируются по расстоянию через `navigator.geolocation`. Добавлен `useGeoLocation` хук, компонент `DistanceBadge` на карточке клуба (1.2 км). Fallback на алфавитную сортировку при отказе в геолокации.
```

### 3. Автоматически определи тип релиза

**НЕ спрашивай пользователя** — определи сам по правилам:

- **major** (X.0.0) — ломающие изменения (breaking changes), полная переработка архитектуры, смена API
- **minor** (0.X.0) — **новые компоненты** (`[NEW]` файлы), новые экраны, новые фичи, новые webhook-и
- **patch** (0.0.X) — всё остальное: рефакторинг, баг-фиксы, правки стилей, оптимизации, обновление зависимостей

**Алгоритм:**

1. Есть ли breaking changes или удалённые публичные API? → `major`
2. Есть ли новые файлы (`[NEW]`), новые компоненты, новые экраны? → `minor`
3. Всё остальное → `patch`

Покажи changelog и выбранный тип — **без ожидания подтверждения**, сразу переходи к шагу 3.5.

### 3.5. Оформи changelog в CHANGELOG.md

В файле `CHANGELOG.md` уже может быть секция `## [Unreleased]` с накопленными изменениями от предыдущих `/save`.

**Действия:**

1. **Переименуй** `## [Unreleased]` → `## [X.Y.Z] — YYYY-MM-DD \`vX.Y.Z\``
2. **Дополни** записями из шага 2.4, если они ещё не записаны в Unreleased
3. **Добавь пустой Unreleased** заново сразу после описания:

   ```markdown
   ## [Unreleased]

   _Нет незадеплоенных изменений._

   ---
   ```

4. Убедись что формат категорий соблюдён: 🆕 Новое / 🔧 Исправления / ⚙️ Инфраструктура / Затронутые файлы
5. Стиль: технический, с указанием компонентов и файлов

### 4. Создай тег и запуши

Сформируй **краткий** changelog (5-7 строк, самые важные пункты) для тела коммита. Это будет видно в Dokploy.

```bash
npm version <type> --no-git-tag-version && VERSION=$(node -p "require('./package.json').version") && git add package.json package-lock.json CHANGELOG.md && git commit -m "release: v$VERSION" -m "<краткий changelog>" && git tag "v$VERSION" && git push && git push --tags
```

Пример коммита:

```
release: v1.2.0

• Live-загрузка клуба
• Расширенная аналитика товаров
• Упрощение настроек API
```

**ОБЯЗАТЕЛЬНО** после пуша проверь что репозиторий чистый:

```bash
git status --short
```

Если есть незакоммиченные файлы — закоммить их ДО завершения деплоя, иначе они «просочатся» в следующий релиз.

### 4.5. Создай черновик релиза в разделе «Релизы» ЕРП (ОБЯЗАТЕЛЬНО)

Раздел «Релизы» (`support_releases`, эндпоинт `/erp/support/releases`) — это **ручной** changelog для клиентов, он НЕ заполняется автоматически. Чтобы релизы не расходились с git, на каждый деплой создавай **черновик** записи. Публикуется он потом вручную в UI (Поддержка → Релизы → ✈️), клиентам до публикации не виден.

Лента общая для всех продуктов LootArena (ЕРП, Приложение, ТВ Виджет, Лид-формы), клиент фильтрует её по продукту — поэтому запись несёт `product = 'clubform'`: без него релиз Лид-форм уедет в ленту ЕРП. Релизы ЕРП (`erp`), Приложения (`app`) и ТВ Виджета (`widget`) заводятся такими же шагами 4.5 в своих репозиториях. Версия уникальна в паре `(product, version)` — одинаковые номера у разных продуктов не конфликтуют.

**Это НЕ технический changelog из шага 2.4.** Перепиши изменения в **клиентские** пункты (highlights) для владельцев/управляющих клубов, НЕ для разработчиков:
- 1–6 пунктов, каждый — про ОДНО видимое изменение: что стало можно / удобнее / надёжнее и ЗАЧЕМ это владельцу. Пункт — до ~250 знаков.
- `title` релиза — **смысл релиза, а не номер**: «Лидерборды: доски лучших гостей и призы за места». Болванка «Обновление v1.153.2» запрещена — в ленте из таких карточек клиент не найдёт ничего (так накопилось 35 неразличимых записей за месяц).
- `description` релиза — **одно предложение-сводка**, за которое цепляется глаз. Пустым не оставлять.
- **Вырежи** внутренние идентификаторы: ID воркфлоу, имена таблиц/колонок/файлов (.tsx/.sql), функций, нод n8n, `$N`, пути миграций, ссылки на CLAUDE.md/specs, названия клубов (For Fame, WEBA и т.п.).
- `category` пункта: `feature` (новая возможность) / `improvement` (улучшение существующего) / `fix` (исправление бага) / `breaking` (ломающее изменение). Ставь по смыслу результата: лента из сплошных жёлтых «Фикс» читается как «у них вечно что-то сломано».
- `type` релиза — тот же, что выбран в шаге 3 (`major`/`minor`/`patch`), КРОМЕ срочного прод-фикса одной проблемы → `hotfix`.
- Тон-образец: заголовок «Видно, какой оператор получает ваши SMS — и сколько он стоит», описание «В аналитике кампании появился разрез по операторам: сколько SMS ушло на МТС, МегаФон, Теле2, какой процент дошёл и сколько стоила доставка.»

#### Подача: пиши от возможности, а не от поломки (CRITICAL)

Клиент читает ленту не как отчёт о нашей работе, а как характеристику продукта, за который платит. Вырезать техническую кухню мало — остаётся интонация post-mortem, и она бьёт по доверию сильнее, чем починка его возвращает.

- Пункт начинается с того, что система делает **сейчас**. Прошлое — только если клиенту надо понять изменение в его работе или в его цифрах, и в фактической форме.
- Заголовок **никогда** не констатирует бывшую поломку.
- Под запретом в клиентском тексте: «не было ни одного», «теперь правда», «врал», «неверные цифры», «был завышен», «тихо», «молча», «незаметно», «впустую», «часто сгорали», «сжигал», «терялось», «дважды», «путал», а также оценочные «честный/нечестный» про свои же метрики.
- Внутренние метрики масштаба инцидента (сколько клубов, строк, рублей, «каждая пятая картинка») в клиентский текст не попадают **никогда** — это ответ на вопрос, который клиент сам бы не задал.

| Не так | Так |
|---|---|
| «У публичной формы не было ни одного барьера» | «Публичная форма закрыта от перебора номеров: …» |
| «„Сохранено“ теперь правда» | «Сохранение с подтверждением» |
| «Эквайринг был завышен — суммы пересчитаны» | «Уточнён расчёт эквайринга — суммы пересчитаны» |
| «Миссия не сжигает накопленное» | «Каждое зачётное действие приносит свою награду» |
| «Аванс больше не выглядит штрафом» | «Аванс учитывается как выплата» |
| «Приз тихо ложился в инвентарь и мог сгореть» | «Победитель узнаёт о призе сразу» |

**Что сохранять обязательно:** если у клиента **изменятся цифры в отчётах** — скажи об этом прямо («цифры в отчёте вырастут: это ранее не отражённые операции, а не новые расходы»). Иначе он увидит расхождение и придёт с вопросом.

**Правки безопасности и разграничения доступа не публикуются.** Отдельное правило, потому что цена ошибки здесь выше, чем у обычного фикса:
- Публичная лента — это подсказка тому, кто захочет проверить, что было раньше. Формулировки вида «доступ закрыт на стороне сервера, независимо от того, что приходит с устройства» или «проверяется по реальной личности» сообщают и о самой бреши, и о том, как она работала.
- Если правка не меняет работу пользователя (в тексте появляется оговорка «работа администратора при этом не меняется») — публиковать нечего по определению.
- Если меняет — кто-то реально теряет доступ — опиши **правило доступа как данность**, без истории и без вектора: «Банковские выписки открывает только тот, кому выдан доступ к финансам». Без «раньше мог любой», «чужие клубы», «на стороне сервера», «с устройства», «по реальной личности».
- Маркеры для самопроверки: `на стороне сервера`, `что приходит с устройства`, `чужой клуб`, `чужие награды`, `по реальной личности`, `подмена`, `посторонние`, `уязвим`.

**Что в клиентскую ленту не идёт вообще:** внутренняя телеметрия и мониторинг, правки внутреннего CRM/поддержки, «на работу приложения не влияет», разгрузка запросов к базе, разовые процессы подключения. Если пункт нельзя объяснить владельцу клуба — он не пункт.

**Самопроверка перед отправкой** (по собранному JSON):

```bash
grep -nEi 'не было ни|теперь правда|врал|неверн|был завышен|тихо |молчалив|незаметно|впустую|сжигал|путал|провал|дыр|Обновление v|на стороне сервера|с устройства|чуж(ой|ие|их)|по реальной личности|подмен|посторонн|уязвим' /tmp/release_draft.json \
  && echo "⚠️ перепиши: подача от поломки или болванка в title" || echo "✅ подача чистая"
```

**Не плоди записи.** Патч/хотфикс отдельной карточкой в ленте не нужен — влей его пункты в ближайший `minor` (в UI: Поддержка → Релизы → «Объединить»). Ориентир — не больше одной записи на 2–4 дня работы.

**Куда писать — прямо в БД, а НЕ в вебхук.** С 25.09.2026 `/erp/support/releases` (WF
`GdJwJJ4Pn0o3Jo8e`) берёт право суперадмина из СЕССИИ (`client-token` → `erp_actor_is_super_admin`),
а флаг `is_super_admin` из тела игнорирует — это закрытая дыра (волна 5 гейтов: флаг из тела давал
любому с секретом вебхука создавать и публиковать релизы). У деплоя сессии нет, поэтому старый
`curl` с `"is_super_admin": true` получает отказ, и черновик молча не появляется. Не «чини» это
возвратом флага из тела и не заводи деплою вечную сессию суперадмина.

Сначала собери пункты в файл и прогони самопроверку подачи (grep выше), потом создай черновик
через MCP `postgres-lootarena` (`execute_sql`). Тексты клади в dollar-quoting `$t$…$t$` — кавычки
и апострофы внутри экранировать не нужно; `highlights` — JSON-массив пунктов:

```sql
-- version = package.json (уже забампан в шаге 4); type — из шага 3 (или hotfix)
INSERT INTO public.support_releases
       (product, version, title, type, status, description, highlights, created_by, created_by_name)
VALUES ('clubform', '<X.Y.Z>',
        $t$<смысл релиза, НЕ «Обновление vX.Y.Z»>$t$,
        '<minor|patch|major|hotfix>', 'draft',
        $t$<одно предложение: главное в этом обновлении>$t$,
        $t$[{"category":"feature","title":"<заголовок про возможность>","description":"<1–3 предложения: что система делает сейчас>"}]$t$::jsonb,
        'deploy', 'Деплой Лид-форм')
ON CONFLICT (product, version) DO NOTHING
RETURNING id, version, status;
```

Пустой `RETURNING` = такая версия уже есть (повторный прогон деплоя): это ожидаемо, деплой не
прерывай. Ограничения таблицы: `product` ∈ erp/app/widget/clubform, `type` ∈
major/minor/patch/hotfix, `status` ∈ draft/published, `UNIQUE (product, version)`. Публикует
по-прежнему человек в UI (Поддержка → Релизы → ✈️).

### 5. Отправь changelog в n8n (уведомление придёт после деплоя)

Прочитай `.agent/toolkit.json` → `project.n8n_url` и `project.deploy_webhook`.

n8n workflow сам дождётся завершения деплоя в Dokploy (90 сек) и отправит уведомление:

- ✅ Если деплой успешен — отправит changelog в Telegram
- ❌ Если деплой упал — отправит предупреждение об ошибке

```bash
curl -s -X POST "<project.n8n_url><project.deploy_webhook>" \
  -H "Content-Type: application/json" \
  -d "{\"message\": \"<CHANGELOG_HTML>\", \"version\": \"v<VERSION>\", \"applicationId\": \"<project.dokploy_app_id>\"}"
```

> `applicationId` — ID приложения в Dokploy. Если не передан — по умолчанию проверяет ERP.

Формат HTML сообщения:

```
🚀 <b>{project.name} v{VERSION}</b>\n\n{CHANGELOG в текстовом формате с использованием \\n для переносов}\n\n📅 {дата и время}
```

> ⚠️ **ЭКРАНИРОВАНИЕ (CRITICAL):** воркфлоу шлёт `message` с `parse_mode: HTML` и НЕ экранирует его. В тело подмешивай ТОЛЬКО валидные теги `<b>`/`<i>`; в самом ТЕКСТЕ не должно быть сырых `<`, `>`, `&` — иначе Telegram падает `400 Bad Request: can't parse entities: Unsupported start tag` и уведомление НЕ уходит (деплой при этом проходит штатно, рвётся только нотификация). Реальный кейс: фраза «матчей < минимума» уронила уведомление v1.107.0 (`byte offset` в ошибке указывает на сырой `<`). Пиши «меньше»/«больше» словами (или `&lt;`/`&gt;`/`&amp;`). Перед отправкой проверь, что в собранном тексте нет сырых `<` кроме тегов: `printf '%s' "$MSG" | grep -oE '<[^b/]'` должно быть пусто.

> Если `project.n8n_url` или `project.deploy_webhook` не заданы в `toolkit.json` — **спроси у пользователя** адрес n8n и webhook-путь, затем предложи сохранить их в `toolkit.json`.

## Что происходит автоматически

1. `npm version` — бампает версию и создаёт тег
2. `git push --tags` — пушит тег в GitHub
3. **Dokploy** получает webhook → видит новый тег → собирает и деплоит
4. **n8n webhook** → отправляет уведомление в Telegram
